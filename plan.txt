ITER: system design and logic overview
======================================

1. Purpose
----------
ITER is a travel money app for Malaysian travellers. It answers one question every day of a trip:
"How much can I safely spend today?" Around that number it offers AI receipt scanning, menu
translation, a tax refund tracker, live exchange rates and a community of shared trip costs.
It is a prototype: it uses a demo trip and moves no real money.

2. Architecture
---------------

   Phone browser / installed web app (PWA)
   +-------------------------------------------+
   | FRONTEND  mobile/                         |
   | Expo + React Native + TypeScript          |
   | screens (src/app) -> state (src/state)    |
   |   -> services (src/services)              |
   |   -> domain maths (src/domain, tested)    |
   | Data saved on the phone (AsyncStorage)    |
   +---------------------+---------------------+
                         | HTTPS, JSON (/api/...)
   +---------------------v---------------------+
   | BACKEND  api/ + backend/                  |
   | Node.js + TypeScript functions on Vercel  |
   |  /api/health        is the server up      |
   |  /api/rates         today's rates vs MYR  |
   |  /api/rate-history  7 or 30 day chart     |
   |  /api/scan-receipt  AI reads a receipt    |
   |  /api/scan-menu     AI reads a menu       |
   +-----+----------------+----------------+---+
         |                |                |
     Supabase        Anthropic API     Frankfurter
     (rate cache,    (Claude Haiku,    (daily exchange
      scan limits,    Sonnet fallback)   rates)
      scan cache)

- The frontend is built into a static web app and served by Vercel; each file in api/ becomes
  one backend endpoint. The logic behind the endpoints lives in backend/.
- Secret keys (Anthropic, Supabase) exist only on the server, never in the app.
- The traveller's trips, expenses and receipt photos stay on their own phone.

3. Main rule: "AI reads, code calculates"
-----------------------------------------
The AI only copies what is printed on a receipt or menu. Every amount, conversion and total is
worked out by small pure functions in mobile/src/domain/, each with unit tests. Money is stored
as whole numbers in the smallest unit (sen, yen) with its currency, so there are no rounding errors.

4. Safe to spend (mobile/src/domain/budget.ts)
----------------------------------------------
Inputs: total budget, reserve (money kept aside), everything spent, days left.

  Today's amount = (budget - reserve - spent before today) / days left including today
                   Fixed for the day while spending stays within it.
  Left today     = today's amount - spent today
  From tomorrow  = (budget - reserve - everything spent) / days after today
  Once today goes over its amount, Home shows the "from tomorrow" figure instead, so the daily
  number lowers live with every overspend.

  Status:
  - Running short: the reserve is being used, or "from tomorrow" is under 40% of the plan
  - Spending fast: over today's amount, or "from tomorrow" is under 70% of the plan
  - On track: otherwise
  (Plan = (budget - reserve) / trip days. Thresholds in mobile/src/config/budget.ts.)

  Demo, day 7 of 10: (2,550 - 300 - 1,450) / 4 = RM 200 a day.

5. Receipt and menu scanning (backend/scan/)
--------------------------------------------
1. The app shrinks the photo and sends it to /api/scan-receipt or /api/scan-menu.
2. The backend rejects anything that is not a JPEG, PNG or WebP under 3 MB.
3. Identical photos are answered from the cache (free, instant).
4. Daily limits per phone and overall protect the AI bill.
5. Claude Haiku returns strict JSON. Code checks it: items add up to the subtotal, subtotal plus
   tax and service equals the total, the currency is supported, the date fits the trip.
   If the numbers do not add up, Claude Sonnet takes a second look.
6. The app shows the result for review, highlights unsure fields, converts to Ringgit, and runs
   the tax refund check. Nothing is saved until the traveller taps Save.
7. With no signal, photos wait in an offline queue and are sent when the connection returns.

6. Other features
-----------------
- Currency: live rates from Frankfurter, cached in Supabase and saved on the phone, so converting
  still works offline. 87 currencies, 110 countries.
- Tax refund: Japan's rules are config (mobile/src/config/taxRules.ts) with a source and a
  "last verified" date; every scanned receipt is checked; a tracker and airport checklist.
- Menu translate: dishes in English, prices in Ringgit including tax and service, pork and
  alcohol flags, and the order can be logged as an expense.
- Community: typical trip cost per destination from shared trips, feed, likes, report and block.
- Plans: 3-day free trial, Day Pass RM 3.50, 7-Day Pass RM 12.90 (purchases simulated). Prices and
  limits live in one config file (mobile/src/config/plans.ts).
- Trip Wrapped: an end-of-trip summary that can be shared.

7. Reliability and safety
-------------------------
- Network calls return typed results instead of crashing; user data is never lost.
- Demo samples still answer if the AI cannot be reached, so a presentation never breaks.
- Accessibility: WCAG AA contrast, 44-point touch targets, screen-reader labels, reduced motion.

8. Testing
----------
- 289 automated tests for the app (Jest) and 59 for the backend (Vitest), plus type checking and
  linting. GitHub Actions runs all of them on every push (.github/workflows/ci.yml).
- Every change was also tried in a real browser before it was published.

9. Build steps
--------------
The app was built in 11 steps, one at a time. Each step had its own Git branch and was only joined
to the main version (main) once its checks passed. The order follows the brief's build order
(docs/PROJECT_BRIEF.md, section 14). What actually happened at each step is in built.txt.

"Checks" always means: type check, lint and all automated tests pass, in both the app (mobile/)
and the backend, and the feature works when tried in a browser.

Step 0. Foundations
  Goal:     A working empty app and backend that the whole team can run and test.
  Build:    Expo + TypeScript project, five tabs (Home, Currency, Scan, Community, Me), design
            colours and sizes in one file, a backend with a health check, automatic checks on
            GitHub, README.
  Done when: the app opens with five tabs, Me shows "Connected" to the backend, checks pass on GitHub.

Step 1. Money core and Home
  Goal:     The main number: how much is safe to spend each day.
  Build:    Money maths as tested functions (amounts in sen), a demo trip, the Home screen
            (safe to spend, spent, remaining, status, daily bars, categories), plan-a-trip form.
  Done when: the demo trip shows the right daily amount, worked out by hand and matched by tests.

Step 2. Currency and manual entry
  Goal:     Log spending in any currency and see it in Ringgit.
  Build:    Live exchange rates (Frankfurter) through the backend, saved on the phone for offline
            use, Currency tab with converter and rate chart, add, edit and delete expenses.
  Done when: an expense typed in yen shows the correct Ringgit amount, also with no connection.

Step 3. Scan backend (AI)
  Goal:     The server can read a receipt or menu photo safely and cheaply.
  Build:    /api/scan-receipt and /api/scan-menu using Claude Haiku (Sonnet as a second look),
            strict answer format, code checks that the numbers add up, daily scan limits,
            a cache for repeated photos, demo samples that work without the AI.
  Done when: sample receipts are read correctly, bad photos are rejected, the key never leaves the server.

Step 4. Receipt scan flow
  Goal:     Photo in, expense saved, in a few taps.
  Build:    Camera or sample photo, "reading" screen, review screen with unsure fields highlighted,
            save, and a waiting list that sends photos later when there is no signal.
  Done when: a scanned receipt becomes a saved expense, and a scan with no signal is sent later.

Step 5. Tax refund
  Goal:     Show travellers the tax they can claim back when leaving Japan.
  Build:    Japan's rules as a config file with source and "last verified" date, a check on every
            receipt, a tracker screen, an airport checklist and a departure reminder.
  Done when: eligible receipts add up correctly in the tracker; rules can change without code changes.

Step 6. Menu translate
  Goal:     Understand a foreign menu and its real price.
  Build:    Dishes in English, prices in Ringgit including tax and service charge, pork and alcohol
            flags, and logging the order as an expense.
  Done when: sample menus show correct Ringgit prices including tax and service.

Step 7. Community
  Goal:     Show what trips really cost, from other travellers.
  Build:    Typical trip cost per destination, feed with posts, comments and likes, report and
            block, and sharing your own trip summary (your expenses stay private).
  Done when: the typical trip figures match the shared trips, and reported posts can be hidden.

Step 8. Plans and Me
  Goal:     The business model: pay only for the days you travel.
  Build:    3-day free trial, Day Pass and 7-Day Pass (buying is simulated), free version,
            My plan screen; all prices and limits in one config file.
  Done when: locked features open after a pass is "bought", and the days counted are correct in tests.

Step 9. Polish
  Goal:     Make it feel like a finished app.
  Build:    Launch animation, welcome screens, button and list animations, demo receipt photos,
            accessibility pass (contrast, touch sizes, screen-reader labels).
  Done when: every screen passes the accessibility checks and animations respect "reduce motion".

Step 10. Final checks and demo
  Goal:     Ready to present.
  Build:    Checks on the live site, a real AI scan on the live server, security check (no keys in
            the app), offline check, demo rehearsal.
  Done when: the whole demo runs on the live site on a phone without errors.

10. How the plan changed
------------------------
The brief was the starting plan. These changes were made while building, each recorded with its
reason in docs/DECISIONS.md:

- Hosting: Vercel + Supabase instead of AWS (Lambda, Secrets Manager). Recommended by the lecturer;
  free, HTTPS out of the box, and much simpler to run. The key still lives only on the server.
- Delivery: a web app installed from the browser (PWA) instead of App Store / Play Store builds,
  because v1 is shown from a server, not the stores.
- Budget: hotels and flights removed. ITER tracks everyday spending only, with four categories:
  food, daily transport, activities, shopping. One simple rule for the daily amount.
- Daily amount and warnings reworked after team testing: one measure drives every warning, and the
  daily amount lowers straight away once today is overspent. The old "money runs out on day N"
  forecast was removed because it could contradict the main number.
- Added beyond the plan: Trip Wrapped (end-of-trip summary), trips to any of 110 countries,
  welcome screens and trip history.
- Not built: opening the app with no connection at all (the team chose not to risk it).

More detail: README.md, docs/PROJECT_BRIEF.md, docs/DECISIONS.md, docs/DESIGN.md.
